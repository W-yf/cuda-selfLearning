# Day 1：对象生命周期、作用域与悬空对象

## 今日目标

完成今天后，应能用自己的话解释：

1. 作用域、存储期和对象生命周期不是同一个概念；
2. 引用和裸指针通常只是观察对象，不会自动延长对象生命周期；
3. 对象生命周期结束后，仍指向它的引用或指针会悬空；
4. 解引用悬空指针或通过悬空引用读取对象属于未定义行为；
5. “程序这次输出正常”不能证明代码正确。

## 核心判断链

面对任何引用、指针或 view，依次问：

1. 它观察的是哪个对象？
2. 该对象的生命周期何时开始？
3. 该对象的生命周期何时结束？
4. 观察者会不会活得更久？
5. 如果会，代码是否在生命周期结束后读取或修改对象？

只要第 4 项为“会”，就必须继续检查第 5 项；不能根据地址里似乎还有旧值来判断安全。

## 三个概念

### 作用域（scope）

作用域主要回答“这个名字在源代码的哪些位置可以被查找到”。离开块作用域后，局部变量的名字不可再使用。

### 存储期（storage duration）

存储期描述保存对象的存储空间至少存在多久。当前先认识自动存储期：普通局部对象通常使用自动存储期。

### 生命周期（lifetime）

生命周期描述某个对象在运行期间何时真正存在。对普通局部类对象，可以先使用这个基础模型：初始化完成后生命周期开始；离开所属作用域时析构，生命周期结束。

存储空间中仍残留旧比特，不代表原对象仍然活着。

## 引用、指针与所有权

- 引用是已有对象的别名，不是被引用对象的所有者。
- 裸指针可以表示非拥有观察；它本身存在，不保证所指对象仍存在。
- 观察者的生命周期可能超过被观察对象，届时它会悬空。
- 把悬空观察者设为 `nullptr` 只能防止之后误用，不能让已经结束生命周期的对象复活。

## 返回值与返回引用

返回局部对象的值通常是安全的：结果对象由语言规则构造在调用方需要的位置，编译器还可以进行复制消除。

返回指向普通局部对象的引用或指针通常是错误的：函数返回时局部对象生命周期已经结束，调用方得到的是悬空观察者。

## 未定义行为

未定义行为不是“必然崩溃”。它可能表现为：

- 看似输出旧值；
- Debug 正常、Release 异常；
- 换一次编译器或增加一行日志后结果改变；
- 崩溃；
- 编译器基于“正确程序不会这样做”的前提进行意外优化。

因此不能通过“运行一次没有出错”验证悬空访问是安全的。

## 今日三个判断场景

### 场景 A：返回局部对象的引用

```cpp
const std::string& make_name()
{
    std::string local{"sample"};
    return local;
}
```

待回答：`local` 的生命周期何时结束？调用方拿到的引用处于什么状态？

### 场景 B：指针逃出内部块

```cpp
const int* observer = nullptr;
{
    int value = 42;
    observer = &value;
}
// 此处还能读取 *observer 吗？
```

待回答：名字 `observer`、名字 `value` 和对象 `value` 分别发生了什么？

### 场景 C：按引用捕获的 Lambda 逃逸

```cpp
std::function<int()> make_reader()
{
    int value = 42;
    return [&value] { return value; };
}
```

待回答：闭包对象仍然存在时，被引用捕获的 `value` 是否一定存在？如何修正？

1. 为什么 `return local;`（按值返回）与 `return reference_to_local;` 的安全性不同？
2. 为什么悬空访问有时还能打印出“正确”内容？这能证明什么？
3. 在场景 A、B、C 中，各自哪个对象先结束生命周期，哪个观察者仍然存在？

## 当前证据

- 已创建概念笔记和独立合成练习入口；
- 安全路径已由 MSVC 成功编译并运行，构造/析构顺序与预期一致；
- 问题 1 已独立回答：能够区分按值返回会建立调用方可用的结果对象，而返回局部对象的引用/指针会留下指向已析构对象的观察者；需要保留的精度是按值返回可能复制、移动或被复制消除，不保证一定发生拷贝。
- 问题 2 已独立回答：能够说明对象析构后存储空间可能尚未被覆盖，因此偶尔读到旧值不能证明悬空指针有效；需要继续保持“旧比特仍在不等于对象仍存在”的区分。
- 问题 3 场景 A 已回答：正确识别 `local` 生命周期在函数返回时结束，但最初混淆了被观察对象与观察者，未识别出返回给调用方的是引用且其状态为悬空引用；经提示后进入相同结构的场景 B 迁移验证。
- 问题 3 场景 B 已回答：能够判断 `value` 生命周期结束后，仍保存其地址的 `observer` 是悬空指针，并说明判断依据；
- 问题 3 场景 C 已判断为不安全，但理由需要复核：返回的可调用对象可以继续存在，真正结束生命周期的是被引用捕获的局部 `value`；
- 新识别的知识断点：此前会使用 `auto name = [] { ... };`，但尚不知道 Lambda 表达式会产生闭包对象，也尚未建立闭包对象与捕获对象生命周期之间的关系；
- 经解释后，已正确识别 `auto reader = [] { ... };` 中 `reader` 保存的是闭包对象；仍需复核引用捕获不延长外部对象生命周期；
- 问题 3 场景 C 的理由复核通过：能够说明局部 `value` 生命周期结束后，闭包对象中的引用捕获成为悬空观察关系；
- 后续学习断点：需要系统学习 Lambda 的闭包类型、`auto` 推导结果、捕获规则以及 `std::function`；Day 1 暂只建立生命周期判断所需的最小模型；
- 闭包类型澄清：闭包对象具有编译器生成的真实、唯一类型，只是该类型没有可由程序员直接拼写的原始名称；它不是 `int`、`float` 这类有语言关键字名称的基本类型，可通过 `auto`、`decltype` 或模板间接指代；
- 问题 4 首次尝试为 `[](int value)`：该方案不捕获外部对象，本身可以安全使用调用方传入的值，但改变了调用签名，不再匹配原来的 `std::function<int()>`，因此不满足只修改捕获列表的题目约束；
- 问题 4 重答为 `[value]`：能够正确将引用捕获改为按值捕获，并保持闭包的无参数调用签名；能够说明安全性来自闭包对象拥有独立保存的值。需要保留的精度是该副本在 Lambda 表达式求值、闭包对象创建时初始化，而不是一定到 `make_reader()` 返回时才产生；
- 最终迁移检查通过：面对新的 `std::string text` 场景，能够独立判断 `[&text]` 在函数返回后悬空，并改为 `[text]`，理由是局部 `text` 生命周期结束而按值捕获让闭包拥有独立副本；
- Day 1 完成，当前掌握层级提高到“2. 能够解释”。这不表示已经能够独立实现完整生命周期工具或分析全部正确性与性能边界。
